# Atomic source and annotation authoring binding

Vellum requires one coherent local publication when an action combines source
changes with authored annotations. Adopted specification 0.210 binds that proposal
to separate source/annotation authority, explicit target bases, owned create
allocation and bounded historical results. This design records the derivation of
that accepted binding, not an additional engine deliverable or public
execute-anything operation. Cross-family outcomes/events remain L02; the selected
U01 receipt facet is implemented in working 0.219 and awaits qualification.

## Existing contract and direct precedent

Requirements §3.8 and specification §§13.6/13.9 permit authored source/annotation
composition while keeping one document owner. Separate commands cannot replace an
advertised atomic action. Automatic annotation placement is also not annotation
authoring: source-write scope does not grant create/body/delete/reattach authority.

LSP WorkspaceEdit is useful precedent for a structured proposal containing
versioned document changes and explicit supported operation/failure kinds. It does
not guarantee one universal atomic transaction: its declared failure strategies
include keeping earlier effects, all-or-nothing application, text-only atomicity
and attempted undo. Vellum's local publication contract retains its stronger
already-adopted boundary rather than selecting a weaker fallback.
[Official WorkspaceEdit definition](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/types/workspaceEdit.md)

LSP change annotations describe changes with labels, descriptions and optional
confirmation. They are not Vellum's persistent authored document annotations.
Do not import UI confirmation/keymap state, file create/rename/delete effects,
JSON-RPC, URI identity or line/character coordinates into this engine proposal.
[Official ChangeAnnotation type](https://github.com/microsoft/vscode-languageserver-node/blob/main/types/src/main.ts)

## Native evidence for the target boundary

The [working native probe](mixed-target-binding-counterexample.mjs) starts with
`abc` and an existing annotation. Standalone annotation-authoring/1 rejects target
range [3,4): it is not part of the current source. A private owned compound can
append `X`, reattach the annotation to [3,4) of its exact candidate, and publish
`abcX` plus that authored target in one publication and one linked history group
with two authored participants. The body remains unchanged.

The probe executes the adopted native modules. It demonstrates that the existing
candidate-target relation is necessary and already supported privately; it does
not establish the public mixed facade, create issuance, result delivery or native
concurrent installation. Exposing the private compound plan or performing text
then annotation in sequence would not close that binding.

The [combined native reference](atomic-authoring-reference.mjs) also composes an
append with all four authoring operations: create, body update, reattach and delete.
The actual shared invocation owner publishes five authored changes in one history
group with four distinct scopes; body and target changes on one record share a
scope. Five conflict controls preserve the complete prior root, including an
invalid final component, duplicate body intent, create/delete identity conflicts
and a foreign candidate descriptor. An injected host protocol fault instead
records Unknown/faulted while preserving the prior root.

Four component receipt-policy checks preflight individual receipt/frame bounds and
capture disclosure ceilings before execution, then construct/release facts from
that exact publication. They cover
present/retained-absent membership, final independent versions, current identity
denial and a too-small reply. The shared coordinator does not yet retain or fund a
mixed receipt vector. This reference is outside frozen qualification and neither
establishes that integration nor proves actual allocation-issuer truth.

The separate specification 0.208/model 0.272 candidate now implements the internal
receipt integration missing from this adopted-baseline probe. Its actual invocation
owner binds and funds a complete immutable component vector, stages it before
root/coarse-fact installation, releases historical receipts under captured/current
grants and retains the original charge through retention/drain-gated forgetting
until owner-controlled retirement. Eleven controls and nine semantic mutants pass,
as do seven adjacent regressions, the registered validator and 121-module boundary/
clean-entrypoint checks. It is frozen for full qualification, not adopted. Its
trusted private preparation port does not validate public per-participant authoring
authority or select public mixed ingress or U01 retrieval.

## Closed proposal recommendation

Use one finite immutable proposal containing typed source intent and the existing
four annotation-authoring operations. Keep a distinct explicit profile from the
source-only exact-source-batch/1 binding; that profile must not silently accept
new authoring fields. A closed compound product is data, not a script, callback,
arbitrary property path, nested transaction or plugin command list. Actual public
entry-point spelling remains specification work, not a new capability decision.

Retain one original authority/engine/invocation context and complete caller intent.
Source entries carry exact incarnations/revisions and original-coordinate complete
edit records, with declared reads/scopes. Normalize repeated source entries and
unordered conjunctions under existing rules; do not reorder authored annotation
operations or erase empty conditions. Capture engine-private source companion
dependencies once; callers need not discover private annotation collections.

Inherit §13.9's same-record rules: a body update and reattachment may combine
using their independent versions and contribute one authored history scope.
Duplicate same-field components refuse; the proposal is not sequential execution
or last-wins assignment. Existing membership validation also forbids create or
delete from sharing that record identity with any other component. Do not invent
references to a preceding create or reorder operations to resolve a conflict.

| Component | Existing authority and dependency meaning to preserve |
| --- | --- |
| Source change | Exact source revision/expected bytes and current F11 source/write-scope grants; all required automatic companions. |
| Annotation create | Current live owner, F13 create authority, engine-owned allocation bound to the original invocation/component, literal body and valid target. No caller-chosen new identity. |
| Body update | Actual record/incarnation and content version, F13 body authority; preserve compatible target/source changes unless declared dependencies require otherwise. |
| Reattach | Actual record/incarnation and target generation, F13 target authority and explicit target basis; preserve compatible current body. |
| Delete | Actual record/incarnation, both content/target versions and F13 membership authority; authored absence is not final identity retirement. |

Mandatory provider/interpretation/policy dependencies remain distinct from caller
assumptions. Every actual write/read participant must be represented and currently
authorized. The engine validates declared assumptions; it does not infer every
semantic dependency of a rename or prove the agent's domain reasoning correct.

## Two explicit target bases

A before-source target names exact starting source evidence and maps through the
proposal's source edits under its declared document/point/range policy. Points
retain explicit position/content profile and affinity. A range is nonempty and
uses checked UTF-8 scalar boundaries. No fuzzy repair, clamping or current-focus
lookup is allowed.

A candidate target refers to the immutable candidate of this same proposal and
the explicit owner document. Its coordinates belong to the fully staged source,
not a guessed future live revision, another proposal or an engine-global current
candidate. Public representation must make that binding unambiguous before
lowering into the existing private descriptor relation. Knowing a descriptor
string is not an authorization grant.

Validate candidate targets only against the exact bounded staged candidate. If
the candidate cannot be constructed or retained, reject the proposal rather than
substitute current source or partially publish the source leg. Source, targets,
automatic placement, authored rows, views and linked history must share one final
decision. No UI geometry, native input state or provider callback belongs there.

## Ownership and results

Create allocations remain engine/supplier-owned, bound to the original component
and limits. Preserve their actual issuance/reservation disposition on refusal,
fault and retirement; do not infer that an identifier was created, erased or made
reusable from the coarse publication result. Actual issuer truth remains a
supplier/refinement gate, not a caller-supplied ID check.

Matching retries retain the same proposal, private dependencies, candidate meaning
and allocations. Changed component intent cannot refresh or replace the claim.
Preparation must fund the complete public/private capture and all actual candidate,
mapping/history/view and receipt/frame obligations before accepting execution.
Provisional refusal refunds only provisional holds; retained stop/fault obligations
require their own protected discharge. No resource-module or persistence effect
is part of this local authored transaction.

One coarse authoritative disposition describes the whole publication. Retain
bounded component-specific historical facts where existing F13 contracts require
created identity/membership or authored versions. Each release meets its captured
ceiling and current per-component authority; source-write success cannot disclose
hidden annotation state. Never reconstruct a receipt from a newer row, report
partially applied components as success, or treat unavailable history as refusal.
U01 still owns how northbound clients retrieve operation-specific receipts; this
working design does not select its route or weaken result meaning.

Malformed, stale, unauthorized or unfunded caller proposals receive the existing
expected refusal disposition before publication. An unexpected internal invariant
or protocol failure is a fault, not ordinary refusal: preserve established
publication facts, retain Unknown where publication is unestablished, fence only
the justified scope and keep outstanding obligations until protected discharge.
Neither a fault nor an unavailable receipt proves NotApplied or promises rollback.

## Remaining acceptance checks

The implementation/reference binding must exercise one actual common coordinator,
not parallel fixtures that merely agree on a success flag. Required cases include
before and same-proposal candidate targets; foreign/mutable candidate substitution;
both point profiles; independent body/target versions; actual create/delete
allocation and retained absence; source/read/annotation permission mismatch;
repeated source entries and conflicting versions; an invalid final component;
complete resource refusal; stale current private companions; current view mapping;
matching/changed retries; cancellation; protected retirement; and bounded historical
result release. Include combined body/target updates, duplicate same-field
refusals, create/delete identity conflicts and fault injection before and after
the publication decision. A rejected component before publication preserves the
current root; faults after publication retain that established publication rather
than manufacturing rollback.

Reuse existing source/annotation/compound/history conditional arguments and finite
checks, then test the new public-to-owned binding seams. Closed finite verbs and
bounded traversals permit a scoped halting argument under trusted execution; they
do not establish categorical completeness, a whole-state bounded lattice, actual
scheduler fairness, physical memory bounds or independent Cleanroom certification.

Existing IF-01/03/08 and INS-01/02/03/06/07/09/13 cover proposal capture, basis/
authority checks, staging, one local disposition, current result release, history,
mapping/views and discharge. MELT/golden/RED distinguish offered, admitted, replayed,
rejected, stopped, faulted and useful whole-operation completion. USE tracks logical
capture/participant/candidate/receipt pressure in declared units. STRIDE challenges
forged bases, wrong-role authority, stale consent and partial installation; LINDDUN
challenges hidden annotation topology, component linkage and retained-content access.
Ordinary telemetry must not contain bodies, source, raw IDs, versions or coordinates.

The 0.209/model 0.273 candidate supplies exact public constructors/normalizers,
owned before/candidate target binding, original create allocation, per-component
native authority and the complete internal receipt path. Sixteen controls/thirteen
semantic mutants, eight omitted fields, 26 permission cases, twelve adjacent
regressions, the exact registered validator and bounded review pass. Its 123-module
boundary and clean-entrypoint checks pass. It is frozen with the receipt work
consolidated for full qualification, not adopted.

At the 0.209 candidate stage, public discovery/enablement, standalone-family
completeness, cross-family result/event assembly and U01 were open. The current
[northbound audit](public-contract-matrix.md) records their subsequent dispositions.
Actual Rust/host/platform/physical/
concurrent/crash and independent-assurance gates remain separate. This adds no new
engine component or public operation family.
