## Adopted defaults and remaining technical work

### 1. Freeze the supported package/host matrix first

Options are a narrow verified reference matrix or a broader initial promise.
Narrow support makes native, asset, resource and compatibility claims testable at
lower cost; its cost is fewer supported environments. Broader support improves
reach but multiplies actual integration and security-maintenance obligations.
Adopted: a narrow explicitly tested matrix, retaining both required thin
reference applications. Do not invent framework/platform versions or a supported
release lifetime before a dependency/license and maintenance review. Host policy
choices need owner approval; internal type/module naming can remain delegated
technical specification work within that accepted matrix.

### 2. Public contracts: closed execution, extensible information

Options are exact closed per-version executable products or broad open-ended
argument/verb bags. Closed products support exhaustive decisions, predictable
refusal and agent discovery, at the cost of deliberate version changes. Open bags
are easier to extend superficially but make surprise behavior and proof scope
harder to control. The closed-execution direction is already adopted, not reopened.
[Neovim metadata](https://neovim.io/doc/user/api/#api-metadata) supplies a direct
typed/discoverable precedent, not a requirement for RPC.

Technical sequence: freeze the minimum supported Rust/host profile before concrete
types, keeping informational metadata evolution separate from executable schema
changes. Rust's
[`non_exhaustive`](https://doc.rust-lang.org/reference/attributes/type_system.html)
permits future variants/fields; using it is not a proof of a closed executable
vocabulary. Exact enum/metadata compatibility policy remains reviewable under
D44. No wire format, stable native ABI or new scripting runtime is implied.

### 3. Line, word and editing profiles

For line recognition, LF/CRLF only minimizes the delimiter domain but treats lone
CR as content. LF/CRLF/CR accommodates common legacy text at the cost of one more
boundary. Unicode extended line separators recognize more prose conventions but
change navigation semantics in files where these characters are ordinary content.
[Ropey's documented feature profiles](https://docs.rs/ropey/latest/src/ropey/lib.rs.html)
show these are real alternatives, not a universal editor rule.
Adopted: LF/CRLF/CR with zero-based UTF-8 byte columns, separate body/delimiter
spans, final empty line after a delimiter and valid EOF caret. CRLF-interior
conversion is unavailable, never rounded. Lossless bytes remain mandatory;
line recognition never authorizes newline normalization.

For grapheme/word commands, a pinned default
[Unicode boundary profile](https://unicode.org/reports/tr29/) gives reproducible
standards-based behavior, but language-specific tailoring may be needed. Broad
tailoring increases linguistic fit and compatibility/test burden. Adopted:
Unicode 18.0.0/UAX 29 revision 49 default extended grapheme and word boundaries;
only explicitly named/versioned alternatives. Section 26.1.2 now defines the
named simple indent/outdent/newline products; keyboard Tab routing, numeric
preferences, optional grammar indentation and other command rules still require
their declared contexts. Selection/grouping baselines remain. Identifier commands use
separate named profiles. Navigation boundaries are not
proof of semantic token identity or automatic target repair.

### 4. Reference comment storage

Options are a small versioned host-owned record format, W3C JSON-LD interchange,
or a host database. A small format is inspectable and easy to test but requires
an explicit schema/migration/association contract. JSON-LD improves annotation
interchange but adds identifier/context/selector semantics beyond v1 needs. A
database offers transactional indexing and host identity management but increases
deployment/portability burden. The
[Web Annotation model](https://www.w3.org/TR/annotation-model/) is useful for
body/target/source-state separation, not a mandate to choose its serialization.

Adopted: a small versioned UTF-8 JSON reference-host format, empty default metadata,
explicit document/source association and staged load; core remains storage-neutral.
The concrete record schema is now §29.4.1. Complete host location/identity,
move/rename, permissions,
external-change, backup and migration rules. A sidecar path by itself cannot prove
identity continuity or independent atomic durability. D20's format family is now
selected; exact codec/binding/migration and native evidence are not closed.

### 5. Assets and definition resolution

Bundled pinned assets improve reproducibility/offline use but create update and
license obligations. Host-supplied compatible assets improve flexibility but need
admission/compatibility and retained-context evidence. Adopted: bundled pinned
reference integration and validation of host-supplied alternatives against
explicit profiles. Actual versions/licenses require inspecting actual candidates,
not filling version placeholders with guesses.

The base authorized preloaded definition closure is now specified; it does not
mean automatic URI fetch. This follows the separation between identifiers and
retrieval in
[JSON Schema 2020-12 core §8.2.3](https://json-schema.org/draft/2020-12/json-schema-core#section-8.2.3).
That document is an Informational Internet-Draft, not an RFC. Actual selected
dialects, recursive validation semantics and execution budgets still need provider
evidence. [SHACL 2017's failure distinction](https://www.w3.org/TR/2017/REC-shacl-20170720/#failures)
supports failure versus conformance separation, not selection of SHACL as a core
dependency or a proof that every validator halts.

### 6. Measurements and operational promises

Fixed universal numbers are simple but unsupported without workload evidence.
Host profiles with measured reference defaults preserve bounded admission and
honest scope but require explicit units, workloads and maintenance. Adaptive
tuning alone cannot replace hard ceilings. The latter two concerns are already
resolved architecturally: hard validated profiles, evidence-based tuning.
Recommendation: select the supported workloads/clock domains, then freeze numeric
defaults/SLOs from measured useful outcomes and saturation, including censored
work and observation loss. Do not add speculative percentile targets.

MELT, golden signals, RED and USE already share the semantic measurements in
specification §23.3; another acronym or duplicate counter is not a missing proof.
[OpenTelemetry's metrics model](https://opentelemetry.io/docs/specs/otel/metrics/data-model/)
can anchor an adapter's units/streams, not its runtime capture overhead or an
automatic exporter dependency. Safe local capture remains separate from drain.

Security ownership is an external fact: select real contacts, supported versions
and response/patch process. [RFC 9116](https://www.rfc-editor.org/rfc/rfc9116.html)
is a useful reporting-route precedent where applicable, but a fabricated
security.txt contact/expiry would not close D47. Review and CI roles likewise
require actual participants and execution, not another self-certified field.
