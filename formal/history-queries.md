# Scoped history inspection

Section 14.5.1 separately adds actual owned native context issuance/current basis
and F04/F14 composition; see [history-contexts.md](history-contexts.md). The older
checker below retains its own narrower scope and exclusions; public acquisition,
encoding and authentic host scope/coverage/retention facts remain separate.

Specification §14.5 selects the three existing F04 query products. A frontier
reference identifies a projected retained group; availability describes its
captured frontier/evidence eligibility; blocking detail contains only permitted
scope/group references. None reserves a frontier, pins unlimited history or grants
reversal rights. Current F14 admission must still validate the whole operation.

## Precedent and boundaries

[Neovim undotree](https://neovim.io/doc/user/vimfn/#undotree()) exposes current undo
position and structured block information. This supports inspectable history,
not exporting Vellum's private linked participant graph or adopting alternate
branch navigation. Vellum's already selected scoped frontier rules remain normative.
No new public operation, transport, history branch or extension runtime is added.

The native semantic catalog is history-queries.json. Every request binds a retained
history context, visible history scope, direction and projection/resource profile.
Availability and detail select either the scope frontier or a projected group.
Source-only access does not imply annotation history inspection or reversal rights.
Context references are selectors, not grants; context issuance and native codecs
are not implemented by this reference. An ordinary source/annotation snapshot is
not silently reinterpreted as a history context.

At capture, derive blocked state from every actual participant frontier, not just
the requesting or visible scope. Valid retained group/evidence and complete history
coverage are prerequisites. Established empty history is distinct from unavailable
evidence, a hidden frontier, an invalidated group or an unknown retention floor.
An eligible result establishes only the captured frontier/evidence predicate;
current identity, rights, content, companions, interpretation, bounds and stop state
remain mandatory at reversal. Inspecting an eligible group before intervening work
cannot authorize undo against the newer state.

Release requires the same recipient, purpose, destination, context, profile, policy
and continuity, plus current grants, live/retained context, transfer capacity and
unchanged history basis. Stale current advice is unavailable, not an invitation
to use the old group as a grant. Narrowing cannot release old richer detail and
broadening cannot expand the captured projection. A newly acquired context may
show the newer state. Authoritative outcome retention is separate from this
evictable inspection context.

Permitted detail is the complete bounded permitted projection, not a complete
participant graph. An empty detail list does not mean no blocker. Hidden participant
names, cardinality, global sequence values and hidden blocking group identities
are absent. Overall blocked/eligible state is the declared operational disclosure
for an inspectable linked group; this reference does not claim noninterference
between worlds with different permitted overall availability. Within resource
bounds, changing hidden blocker identity preserves all visible products.

## Executable evidence

history-queries.mjs imports the actual normalized compound publication/reversal
functions. It constructs a group spanning two source documents, then a later group
on the second document. Inspection blocks the first group from the first scope;
actual undo of the prerequisite makes it frontier eligible and actual complete
reversal applies. Revoked write authority still refuses that reversal.

The checks cover 192 release gate combinations, 24 paired hidden-blocker comparisons
and 49 controls, including empty versus missing history, per-direction frontiers,
wrong contract/fields/selectors, private raw identities, capture/detail bounds,
owned capture/result copies and diagnostic independence. Five in-memory mutants
must load successfully and then fail assertions: omit another participant's
frontier, ignore history freshness, ignore current projection, expose a private
blocker and treat an unknown floor as empty. The last control explicitly selects
the current frontier on an otherwise empty fixture, avoiding an unrelated missing
group failure that would conceal a faulty empty-history rule.

Inputs are normalized trusted values under a bounded profile, not hostile decoded
native objects. Registry integrity, owner-issued projection bindings, complete
history floors and retained evidence truth are premises. Logical JSON byte charges
are fixture units, not physical memory or native transfer bounds. Context capture,
issuance, atomic root/current-policy truth, held-root discharge, concurrent release,
full reversal eligibility, create/delete history, general target restoration and
production/native refinement remain open. These same-author sensitivity tests are
not independent Cleanroom certification or additional solver theorems.

## Instrumentation

INS-06 observes capture, scope/direction resolution, actual frontier/evidence
classification and bounded permitted projection. INS-03 observes final release or
recipient-safe unavailability; INS-08 accounts retained contexts and inverse/group
pressure. INS-02 separately records actual reversal publication and INS-12 diagnostic
loss. MELT/golden/RED distinguish inspection attempts, available/empty/blocked/
unavailable products and capture/release phase latency from actual reversal counts.
USE applies to real registry/retention/transfer resources, not a fabricated CPU
metric per query. STRIDE/LINDDUN challenge forged selectors, policy expansion,
cross-recipient linkage and private blocker leakage. STPA/FMEA challenge stale
eligible advice, incomplete linked validation and unknown history mislabeled empty.
No scope/group/context identity or hidden count becomes an ordinary metric label.

This inspection slice makes no point-storage claim. Section 29.4.1 separately
fixes the approved explicit profiles; native persistence integration remains open.
