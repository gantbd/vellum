## Precedent and closed inputs

The native Rust live-relation refinement now implements owned attach, exact detach
and membership over the existing actual publishers. It captures one bounded
original request/context/target interpretation under real parent funding before
copy/preparation, without retaining a candidate root or view snapshot. Fresh
service checks applicable rights and reconstructs using current targeted native
guards/caps/promise floors; unrelated publication does not itself stale the job.
The publisher stages its historical changed fact before installation. Under
serialized exclusive ownership, truthful host policy/retention premises and the
trusted assignment boundary, immutable interpretation plus pending-only service
prevents replay publication; original ticket/marker/candidate/terminal correlation
and captured/current release checks prevent a newer relation from rewriting history.
Bounded normalization and closed operations add no unbounded interpreter. Expected
refusal and Unknown interruption remain distinct; protected cleanup cannot settle
Unknown or refund unrelated holds. Rust tests cover these claims' selected paths,
not the JavaScript writer-inspection envelope, frozen proof/hash recertification,
complete public decoder integration, crash atomicity or physical/latency qualification.

Explicit native F06 V5 now composes those retained results. Admission binds its
version/lifecycle ceiling and complete logical wrapper to the original observer;
release intersects common original/captured/current permission with native result
authority. Thus, under the existing truthful-host/exclusive-owner premises, a
successful V5 live-relation result implies release of that same original native
decision, not fresh execution or a current-row inference. Prior profiles cannot
upgrade and receipt faults absorb only the receipt facility, preserving protected
status and independent cleanup. Rust acceptance/fault tests exercise this
refinement; they do not recertify the JavaScript model or prove wire/physical/
concurrent/crash/independent assurance.

The coordinator obtains the actual native root and uses the actual selected

## Trusted-native behavior facade (not reference-envelope decoding)

`document_facade.rs` supplies closed native submit/service dispatch over the same
scratch owner, three live relations and original prepared-disposal owner. Matching
command/admission families delegate exactly once; mismatches return unavailable
before native work. Fresh service delegates to the selected existing owner, whose
original ticket/context, current rights, stop and publication guards are unchanged.
Consequently the facade inherits each owner's conditional publication/retention
properties without introducing a second execution record or result authority.
Dispatch itself has no loop, callback, name resolution or new allocation; its
termination reduces to the existing bounded native operation. An unexpected
service panic is resumed with its original payload and separately observed Unknown,
not converted into success, rollback, known refusal or hold discharge. Native Rust
acceptance/fault tests check these claims; they do not independently certify them.

This is deliberately not a refinement claim for the complete reference F17 data
envelope. That envelope uses string invocation values and explicit disposal
serialization/binding/disposition data. Native opaque roles and an exact prepared
disposal cannot silently replace those fields or establish retention/discard
authority. Full data-envelope decoding/current-release/discovery remains open.

The closed native V2 facade now includes unchanged V1 and explicit prepared
disposal without extending V1's exhaustive types. Matching explicit admission/
service retains every applicable original/current check; mismatched families and
legacy service cannot execute that explicit intent. The dispatch call graph is
acyclic: V1 lifts into V2; V2 goes directly to a private legacy dispatch or the
native explicit service, never back to public V1. Thus composition adds neither
an interpreter nor another execution record. One outer facade observation/fault
boundary remains, while actual native observations retain their separate meaning.
Rust tests check V1 exhaustiveness, all four explicit disposition combinations,

## Data-first native disposal admission and replay

`DisposalInput` is a closed prepared-or-request input to the same native admission
function. It does not install another owner. Applicable authority, original full
context/limit/epoch/ceiling checks and existing intent comparison occur before
fresh metadata access. A matching admitted request returns that original phase
without reaching the preparation branch; equality of the full captured explicit
request plus its independent witness prevents a changed request from substituting
another plan. Thus pending replay cannot refresh a stale root, and disposed or
forgotten replay cannot create fresh work. Already prepared inputs retain their
existing exact-root comparison and profile isolation.

Only a fresh issued ticket with no intent reserves actual parent capture and
prepares its explicit expectations. Successful preparation is captured by the
existing original owner and actual publisher; a declared preparation refusal
refunds only the provisional reservation and does not install intent. An
unexpected preparation product fences Faulted, rather than acquiring a made-up
ordinary rejection class. This relies on the existing pure native preparation
contract; it does not establish rollback of callbacks or external effects.

Rust tests exercise replay after real publication/forgetting, pending replay after

## Registered views and workspaces

Attach an existing unbound registered view to a live owner under exact lifecycle,
source and view attachment generations. Reuse the existing scalar-UTF-8 byte
boundary checks and canonical positional selection normalization, including
overlap merging, caret deduplication, direction/affinity and primary selection.
Do not steal a view from another document or silently round a byte position.
Advance attachment, selection and viewport generations together; preserve the
view's other declared metadata and all unrelated views.

Detach only the exact current association. Clear its document/source association,
selections and primary marker, and advance the same three generations. An owned
selection plan prepared before detach/reattach cannot become current again. Last
view detachment neither disposes the document nor releases storage/provenance.

Membership changes only the named current workspace's document-identity relation
and generation under workspace-read/membership-write authority. The same document
owner may belong to multiple workspaces without copying source or annotations.
Removing the last membership does not dispose it. A current already-satisfied
membership is unchanged without publication; a stale workspace generation still
refuses, even if the desired membership happens to match.

Relation work does not advance the document lifecycle, source or annotation-set
generation. A lifecycle generation at its ceiling does not by itself block a
relation operation that leaves that generation unchanged. Counters that actually
advance must have room. Disposed owners remain concretely fenced despite positive
supplied liveness facts. View/workspace registration, presentation capabilities
and host authority are separate prerequisites, not created by these products.
