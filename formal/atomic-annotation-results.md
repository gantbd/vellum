# Native compound annotation receipt ownership

Specification §13.9.6 composes existing annotation-result policy with the actual
shared invocation coordinator. It retains one historical receipt for each authored
annotation component without exposing a private plan as public ingress or choosing
U01's public result-retrieval route.

## Original binding and logical funding

First-party preparation normalizes the whole compound, derives each receipt's
operation/record identity from that plan and binds an opaque hold to its actual
parent/domain/ticket. It captures individual policy ceilings after complete result
and release-frame preflight. A caller cannot supply an unrelated receipt target
vector. This internal trusted port does not perform the public mixed facade's
separate [per-participant authoring checks](atomic-authoring.md) or establish
allocation-issuer truth.

For n bounded authored components, the actual parent reserves 2B + 3nM logical
serialized bytes, where B is the retained plan/descriptor/ceiling frame size and M
is maxResultBytes. B must fit maxIntentBytes. Checked arithmetic and current parent
headroom guard the debit. Two metadata frames and staged/retained/release result
frames are bounded; existing root/candidate reservations remain required. This is
not RSS accounting, allocator/copy-peak measurement or a new independent budget.

## Adopted native create-grant refinement

The user selected original-component-scoped create-result authority. A trusted
grant names the original invocation/authority/document and annotation-component
ordinal. The actual native owner binds that locator to its immutable normalized
plan and exact allocated annotation; the locator alone grants nothing. Separate
ceilings prohibit sibling disclosure. Existing-record grants stay exact, and a
current create grant may use the original component scope or exact allocation.
The standalone invocation-scoped product is not broadened.

In the Rust refinement, preparation establishes that binding before exposing
admission, using the real parent's checked `2B + 3nM` reservation. Publication
rechecks the original native plan/component correspondence and stages the whole
vector from the final candidate before any root assignment. Delivery requires a
retained known terminal outcome, original owner/funding/plan identity and the
captured/current capability meet. Hence, conditional on truthful host grants,
serialized exclusive ownership and nonthrowing trusted installation, a grant
for original create component i cannot deliver component j's identity for i ≠ j;
replay cannot allocate a replacement or widen its original ceiling. The four
operations and bounded component/vector scans add no unbounded interpreter.

The existing JavaScript reference evidence below uses exact original allocation
targets. It does not itself prove this new preallocation grant syntax or native
implementation. Rust acceptance cases exercise sibling rejection, all 25 field

release, funding/cleanup, plan substitution and interrupted installation. Applied
means whole-compound publication, including unchanged fields. Interrupted native
installation is fault-fenced Unknown with no deliverable success vector, not
crash rollback. No frozen hash/suite recertification is claimed by these cases.

The native F06 V4 refinement now composes that retained producer through an

## One installation and historical release

The coordinator validates the original hold/plan relation and stages every receipt
from the same final candidate, after native and outer-root validation. It installs
the root, coarse facts, vector and done phase with the existing trusted assignment
boundary. A known refusal yields no record facts; unexpected protocol failure
discards the vector, preserves the original root and records Unknown/faulted.

Individual first-party release checks current outcome eligibility, the original
component index and exact current record/invocation grant, intersected with that
component's original ceiling. It never consults current source/annotation rows.
An admission with no result grant may publish while remaining unable to disclose
identities later. Current permission cannot enlarge the admission ceiling.

Retention/drain-gated forgetting clears actual receipt storage and the coarse
result. Strict Boolean checks apply to the new path, without inventing an owner-
control requirement for ordinary annotation-result eviction. The plan/ceiling hold
and its charge remain until separately owner-controlled retention/drain retirement.
Retirement invalidates the hold and refunds the actual parent once, even when the
owner is faulted; it does not reset faulted health or spent invocation issuance.

## Conditional preservation and halting arguments

Assume bounded normalized private plans, truthful current host/grant/retention
facts, complete ordinary compound authority checks and serialized, non-reentrant,
nonthrowing trusted installation. Preparation establishes immutable plan/component
correspondence and a parent charge that includes the bounded vector frames.
Every stage uses that same correspondence and candidate. No receipt is installed
before all components and the coarse terminal fact are ready. Therefore native
publication and retained component facts agree at the observable boundary.

After installation, receipts and ceilings are immutable. Release depends on those
values and current grants, not newer rows, so later edits cannot rewrite historical
versions. Forgetting removes the complete vector but leaves the ticket spent and
the original funding held. Retirement's exact parent/hold binding and deletion
permit at most one refund. These arguments concern this reference boundary, not
crash atomicity or actual provider truth.

The operation sum is the existing four F13 operations; preparation, staging and
release traverse bounded captured vectors and finite existing helpers. Under the
trusted-execution assumptions each call halts or faults. This does not establish
whole-engine categorical completeness, lattice closure or scheduler fairness.
