# Engine and frontend boundary evidence

## Current engine integration and presentation partition

Specification 0.214 §1.1 and requirements §§3.1/3.3/10.1 assign five clipboard
workflow variants to a headless integration facade: F22 read, F23 copy/cut export
and F11 accepted-paste/validated-cut-deletion. The full 87-variant editor catalog
now partitions into 71 engine, five integration and eleven presentation variants.
Integration is not UI, and none of the required transfer behavior is removed.

The engine and integration decoders independently project their declared owners
from unchanged editor-wide family indices. Each projection checks 44,544 finite
gate cases on typed and dynamic routes. Eighteen controls check total/disjoint
ownership, original indices, copied inventory, malformed/unknown refusal and
declared static imports and immutable returned descriptors. Ten semantic mutations
challenge cross-owner routing, inventory leakage, descriptor tampering and
renumbering after a coherent baseline. Syntax/import errors
do not count as behavioral detection. The existing 121 frontend traces and ten
undispatched integration-routing frames preserve an actual engine root and usage.

The selected engine/reference graph still has 124 modules without frontend
helpers. Combined clipboard references remain co-located proof harnesses; this
check explicitly does not establish a clipboard-free kernel graph, complete
integration execution, public request/task/replay assembly or production package
separation. Those obligations cannot be closed by relabeling code or removing
workflow rows from the engine inventory. No new execution/provider semantics,
solver condition or numerical deployment limit is added. Full frozen
qualification and endpoint adoption remain pending for this draft.

[ownership-discovery-checks.mjs](ownership-discovery-checks.mjs) crosschecks the
thirteen existing native metadata profiles with the engine inventory. All 43
current metadata variants are engine-owned, and none names an integration
workflow. Six oracle sensitivity controls reject changed ownership, metadata
coverage and original indices. This crosswalk does not prove handler execution.

The older 76/11 counts below describe preceding qualification scopes and are
superseded by this three-owner partition, not requests to restore clipboard
workflow verbs to the semantic engine.

## Reference facade and ownership

[engine-facade.mjs](engine-facade.mjs) exposes engine-only typed/dynamic decoding,
routing and discovery metadata. Presentation requests have no engine route.
Original family indices remain stable; filtering discovery must not renumber
typed commands. F16 now names `semantic-settings`; the former `settings-keymap`
label is unsupported. Neither label is a frozen Rust API. Specification §22.3.1.1
now selects bounded structural settings arguments; actual registered types,
semantic resolution and native activation remain open. See semantic-settings.md.

The presentation partition covers geometry inspection, visual-navigation target
resolution, viewport policy, geometry work/results and UI-specific host facilities.
Logical selection/navigation, source edits and applicable effect/authority/evidence
guards stay in the engine. Host implementation of OS services remains outside it.

The useful helper is [frontend-keymaps.mjs](frontend-keymaps.mjs), exercised by
[ratatui-keymap-reference.mjs](ratatui-keymap-reference.mjs).
[frontend-configuration-reference.mjs](frontend-configuration-reference.mjs)
preserves the earlier combined fixture and its eight mutation checks as frontend/
editor-integration evidence, not a joint engine/UI publication guarantee. No Rust
ratatui application implementation is claimed. Iced may reuse this optional helper.

[CodeMirror's view-package keymap implementation](https://github.com/codemirror/view/blob/main/src/keymap.ts)
is direct precedent for placing key interpretation above state/transactions, not
proof of Vellum's ownership, authority or concurrency properties.

presentation and integration owners instead of inferring expected results from
the manifest. Typed/dynamic routing agrees across 44,544 variant/gate cases for
each projection. Eighteen controls cover partition totality, unsupported old
verbs/versions/owner fields, stable indices, copied metadata, immutable
descriptors and declared static imports. The engine facade
and invocation-publication entry points, together with the semantic-settings
argument normalizer, native settings state, recipient reader and configured line consumer, reach 124 local modules without importing
the relocated frontend modules. This is static local import evidence, not proof
about arbitrary dynamic loading or Rust linkage. Tests may import both layers.

An actual owned native invocation domain preserves exact root identity and usage
through 121 frontend key traces up to length four, including undispatched command
intents. This bounded frame check does not prove every UI or dispatched edit.
[engine-ui-mutations.mjs](engine-ui-mutations.mjs) checks an unchanged coherent
graph before requiring ten assertion failures for cross-owner admission,
swapping owners, inventory leakage, descriptor tampering and renumbering typed families. Import
or syntax failures do not count as mutation detection.

## Remaining refinement and observation

Registered engine setting semantics and owned activation, every native gateway's use of this
projection, optional-view/host integration, production package dependencies,
real frontend/platform behavior and independent assurance remain open. The
retained combined fixture is not that implementation. No new solver theorem or
whole-engine categorical closure is claimed.

Command metadata may carry frontend default-binding suggestions without making
bindings engine registry state or admission preconditions. Settings resolution
and activation follow each setting's owner; frontend keymap conflicts cannot
block a headless semantic request. Native accessibility adapters compose engine
semantic reads/actions with frontend focus and geometry. These ownership rules
also govern the configuration and accessibility sections, not only key handling.

Specification §22.1.6 adds a fixed F13/F14 declaration producer from the actual
reference handlers. Private origin survives current discovery and rejects generic
lookalikes; it introduces no UI bindings or additional command store. See
builtin-discovery.md for selected field/origin evidence and remaining all-family,
value-codec, policy/host and production refinement gates.

INS-01/02/03 observe engine admission/publication/release; INS-11 observes frontend
input, chord and native presentation milestones. INS-09 attributes configuration
to its owner. UI-only activation is not an engine invocation/document publication
population. Separate UI callback and engine execution latency; ordinary metric
labels exclude raw keys, targets and content. Golden/RED/USE/MELT and
STRIDE/LINDDUN retain that interface attribution.
