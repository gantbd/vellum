## Intent and current native interpretation

`registration-invocations.json` defines the private reference wrapper:
registration-invocation/1, activate-context, native-resource-registration/1,
invocation and request. Request is the existing exact `{changes}` batch, not an
open argument bag. Native validation retains the two tables, two actions, three
row products, exact present/absent expectations, duplicate-slot refusal and finite
lifecycle/membership/bindings profile from [resource-registration.md](resource-registration.md).
The wrapper adds no new registration semantics or provider capabilities.

One immutable plan binds actual invocation owner/domain/ticket/reference, request
and profile. Relation, document-lifecycle and registration preparations exclude
one another on an issued slot; a prepared slot cannot submit another job or plan.
Admission validates the complete existing invocation context and strict facts,
reserves bounded intent/outcome bookkeeping and captures its trusted-host result
ceiling. Repeated matching submission observes the same pending/terminal job.

At service, recheck literal-true registration interpretation and the exact retained
profile. Prepare from the actual current root and private registration floor,
using the same native candidate/certificate and final validation as direct native
activation. Unrelated source or catalog publications can survive: this is a
retained batch intent, not permission to install an old candidate. A same-slot
expectation mismatch refuses; an unrelated registration change may raise the
fresh batch stamp without changing the requested slots or configuration.

## Floor root outcome and receipt

Stage the native certificate, candidate and copied invocation-attributed native
result before committing. The common owner checks actual root and future-baseline
promise limits, materializes the complete outcome, freezes the candidate and
carries actual source-journal identities. Final commit binds exact stage/plan/
owner/domain/ticket/before-root/result/receipt, current interpretation/profile,
native candidate/result/floor reconstruction and current native facts.

The native helper materializes its return value before updating the private floor
and consuming the certificate. Then the owner installs root, outcome, receipt and
terminal phase in the same synchronous trusted turn through bounded assignments.
There is no await, provider callback, nested root publisher or user code between
floor commit and terminal tuple installation. This is serialized reference
atomicity, not a concurrent or crash-durable implementation guarantee.

Applied batches advance publication once. Empty/identical or already-absent removal
batches remain validated unchanged with the exact root pointer and no fresh stamp.
Removal never lowers the floor; reinstallation receives a later stamp. Queued stop,
stale expectations, incompatible interpretation, capacity/promise failure and final
certificate contradiction do not partially update the catalog or floor. Protocol
contradiction faults the invocation without fabricating successful activation.

Existing producer ledgers, unresolved effects, registrations captured by earlier
work, authored documents, bindings, baselines, histories and view/workspace state
remain framed by the native product. Registration withdrawal is not cancellation,
quiescence, binding release, provider termination, refund or physical revocation.
Replay, result forgetting and invocation retirement cannot reapply or recycle the
registration clock; retirement forgets the retained preparation.

## Trusted host result boundary

The receipt is the existing copied native `{status, registrations}` result plus
invocation. It retains requested table/provider/resource and resulting generation
or null for absence, not unrequested rows, locators or configuration payloads.
Native generation values remain owner-wide internal stamps; possession of a
receipt is neither activation authority nor a supported unprivileged encoding.

Require the captured exact-true registrationHostResultAllowed ceiling and current
exact-true registrationResultReadable, registrationResultContextCurrent and
registrationHostResultAllowed facts, complete original invocation context,
permitted outcome summary, ordinary current release gates and current result-byte
limit. Later permission cannot widen the captured ceiling. A result may be withheld
without changing the committed outcome. Forgetting removes it without reopening
execution. The embedding must supply truthful trusted-host classification and
grants; these Boolean premises do not prove a sandbox or identity oracle.

Do not expose these raw stamps through a remote or unprivileged adapter. Scoped
public registration references, non-linkable stamp encoding, discovery and events
remain explicit technical gates. This restriction preserves the earlier native
boundary; the new receipt is not a claim that raw global counters are private.

## Conditional preservation and termination

Assume private trusted stores/factories, supported known bounded catalogs, truthful
host authorization/identity/coverage/retention/result classification, a unique
serialized non-reentrant owner and existing producer-consumer contracts.

1. **Reduction.** Owned preparation/service use the same native candidate and
   certificate as direct activation. Current validation reconstructs the same
   root, requested result and clock delta; the owned wrapper changes attribution,
   scheduling and release, not row semantics. Native frame/nonreuse obligations
   therefore remain applicable to each supported success.
2. **Atomic settlement.** All fallible candidate/outcome/receipt construction and
   root/promise checks precede floor commit. Final exact identities and native
   revalidation exclude stale or substituted stages. The synchronous bounded
   floor/certificate and root/outcome/receipt/phase assignments form one local
   reference transition. Refusal or prepublication stop changes neither catalog
   nor floor. No provider or distributed transaction is implied.
3. **Attribution and nonreuse.** Native registrationFloor never decreases; removal
   and unchanged success issue no new stamp. Owned retirement/replay do not change
   that rule. Existing captured work remains attributed and charged independently
   of current metadata. Unrelated catalog activity can advance the next accepted
   stamp, which is why this native receipt is trusted-host-only.
4. **Closed finite execution.** The exact wrapper and native batch vocabulary
   reject surprises. Invocation phase progresses issued → pending → running →
   done, with faults represented by terminal outcome/owner fault state, not a new
   retry loop. Finite validated profile bounds constrain every scan/copy. This
   proves conditional per-turn halting, not service latency, fair scheduling,
   provider termination or whole-engine categorical/bounded-lattice closure.

These are authored conditional arguments backed by scoped executable evidence,
not machine-checked module refinement or independent Cleanroom certification.

## Instrumentation and threats

Reuse IF-01/03/04/07/08/10, DAT-09, PATH-01/05/10/12 and
INS-01/02/03/04/08/09/12/13. Separate registration admission, waiting, native
activation, floor exhaustion, unchanged success, current receipt release and
consumer staleness from provider dispatch/completion. MELT records bounded phase/
outcome/refusal observations; RED/golden signals cover admission-to-terminal and
release pathways; USE tracks slots, intent/result/root bounds, retained work and
baseline promises. These are capture contracts, not measured production signals.

STRIDE covers plan/stage substitution, stale catalog activation, forged capability
declarations, receipt tampering and capacity exhaustion. LINDDUN covers linking
unrelated activity through owner-wide stamps and resource identity disclosure.
Keep raw registrations, stamps, invocation/resource/provider IDs, locators and
configuration out of metric labels and unauthorized diagnostic capture. Trusted
host receipt release is not permission to export those values as telemetry.
